# P450 Clean Build and Standalone Runtime Implementation Plan

> **Execution:** Use subagent-driven development with TDD, specification
> review, code-quality review, and evidence-based verification at every task.

**Goal:** Establish the P450 side of Simulation Platform V1.0 as a cleanly
buildable, dependency-explicit component, then prove one isolated headless
P450 + D435 + PX4 + MAVROS runtime before any shared-world integration.

**Scope:** Every write remains below
`/media/lu/P450_PAPER/SIM/p450_sim_v1`. The paper repository and all external
checkouts remain read-only. This milestone does not build Ground, introduce a
joint world, start MoveIt, execute a flight mission, or claim sensor/TF/runtime
success before the corresponding live checks pass. MID360 is a later, separate
gate because its plugin has an independent protobuf/asset closure.

**Baseline:** `c610b7107575ab1d179a2f44047e9bd799eed311` is the reviewed
runtime-only foundation. Its immutable source snapshot and overlay ledger stay
authoritative; every inherited file changed here must be added to
`config/runtime_overlay.json` with its exact current SHA-256.

**Environment contract:** Build from `/opt/ros/noetic` only. Do not inherit the
user shell's `CMAKE_PREFIX_PATH`, `ROS_PACKAGE_PATH`, `PYTHONPATH`,
`LD_LIBRARY_PATH`, or `GAZEBO_*` values because they currently shadow Noetic
with old Prometheus and MAVROS workspaces. Put `ROS_HOME` below repository-local
`logs/`. PX4 is an explicit external runtime dependency pinned to commit
`713814f4eea5990e49dd776a38a36ad53e171f60` and SITL Gazebo commit
`9566172e7c0760f66681304b963d675c5b120daf`; it is not a build dependency and is
not vendored into this repository.

### Step 1: Write and implement the clean Noetic shell contract

Add a RED test before the script. The wrapper must start commands through
`env -i` and allow only a literal base environment: the canonical login user's
actual `HOME`, `USER`, and `LOGNAME` values unchanged; a fixed system/Noetic

environment. Source only `/opt/ros/noetic/setup.bash`, then execute the supplied

### Step 2: Configure an isolated workspace profile

Run Catkin Tools only through `scripts/with_noetic_env.bash`. Configure this
repository as the workspace, extend Noetic, use a merged devel space, select
`/usr/bin/python3`, and use `RelWithDebInfo`. Do not source any workspace below
`/home/lu` or the paper repository. The exact configuration invocation is:

```bash
scripts/with_noetic_env.bash catkin config --workspace "$PWD" \
  --profile p450-clean --init --extend /opt/ros/noetic \
  --merge-devel --install --install-space install/p450-clean \
  --log-space logs/catkin \
  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo \
               -DPYTHON_EXECUTABLE=/usr/bin/python3
```

Run `rosdep check` in a separate read-only clean environment for only the five
selected P450 packages. Clear ambient ROS/Catkin/Python/library/Gazebo
variables, preserve the canonical login `HOME`, and do **not** override
`ROS_HOME`, so rosdep can read the already-initialized host cache. Do not run
`rosdep update`, access the network, copy the cache, or install anything. Do not
include Ground or Livox; their later/legacy keys would create unrelated
failures.

```bash
p450_login_uid="$(id -u)"
p450_login_name="$(id -un)"
p450_login_home="$(getent passwd "$p450_login_uid" | cut -d: -f6)"
env -i HOME="$p450_login_home" USER="$p450_login_name" \
  LOGNAME="$p450_login_name" SHELL=/bin/bash LANG=C.UTF-8 \
  PATH=/opt/ros/noetic/bin:/usr/bin:/bin:/usr/sbin:/sbin \
  /bin/bash --noprofile --norc -c \
  'source /opt/ros/noetic/setup.bash && exec "$@"' bash \
  rosdep check --ignore-src --rosdistro noetic --from-paths \
  src/p450/prometheus_msgs src/p450/realsense_ros_gazebo \
  src/p450/prometheus_gazebo src/p450/prometheus_uav_control \
  src/p450/brick_aerial_perception
```

### Step 1: Define ownership before live launch

Separate world ownership immediately:

- `p450_runtime.launch` owns exactly one P450 model render/spawn, one PX4, one
  MAVROS, UAV control, and its canonical TF publishers, but never starts
  Gazebo;
- `p450_standalone.launch` owns exactly one Gazebo world and includes
  `p450_runtime.launch` once;
- the later joint-world entrypoint will include `p450_runtime.launch` without
  inheriting another world server.

Freeze:

- one vehicle namespace (`/uav1`);
- one world frame (`world`);
- one authoritative dynamic vehicle root;
- one complete D435 chain matching actual message frame IDs;
- PX4/MAVROS namespaces and ports;
- required D435 image, depth, camera-info, IMU, odometry, state, and TF outputs.
- simulation time enabled consistently through the standalone chain;
- explicit Gazebo model/plugin roots for the real Prometheus and external PX4
  assets, rather than ambient paths from an old workspace.

Before live startup, use ROS launch parsing plus node lookup to prove every
included file and executable resolves through the clean runtime environment.
Parsing success is explicitly not runtime success.

The current inherited launch publishes overlapping `base_link`/camera static
transforms while `world_tf_bridge.py` publishes a second camera chain. Tests
must detect duplicate-child TF authorities and disagreement between launch,
model plugin frame IDs, and perception configuration before any repair.
They must also assert that the platform launch invokes
`sim_platform_bringup/px4_sitl_node.bash` and never the external
`px4/px4` ROS-node lookup.

Freeze this unique-authority matrix in YAML and tests:

```text
world -> uav1/base_link                     uav_estimator (dynamic)
uav1/base_link -> uav1/camera_link          uav_estimator (dynamic)
uav1/camera_link -> uav1/camera_depth_frame platform static TF
uav1/camera_link -> uav1/camera_ired1_frame platform static TF
uav1/camera_link -> uav1/camera_ired2_frame platform static TF
uav1/camera_link -> uav1/camera_imu_link    platform static TF
uav1/camera_link -> uav1/d435i_link         platform static TF
uav1/camera_link -> uav1/camera_color_optical_frame platform static TF
uav1/camera_depth_frame -> uav1/camera_depth_optical_frame platform static TF
```

Derive and freeze the static values from the imported D435/P450 model; do not
invent offsets. Launch `uav_control_main` locally rather than including its
inherited wrapper, load the inherited controller settings, then override the
D435 sensor offsets with the exact model-derived values before the process
starts. This keeps `uav_estimator` as the unique `camera_link` owner without
editing it. Disable MAVROS `tf/send` in the local launch after loading its
inherited parameter file so it does not create the disconnected
`map -> map_base_link` branch. Do not start the inherited static TF nodes or
`world_tf_bridge.py` in this milestone.
